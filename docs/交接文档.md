## 0e. ✨ 2026-10-27 蓝牙耳机连接提示

> 需求来自功能清单第 1 条「蓝牙耳机状态弹窗」。**只做了连接状态，没做电量** ——
> 原因见 0e.1，这是实测结论，不是偷懒。

### 0e.1 为什么没有电量

把用户的耳机连上后实测（联想thinkplus-LP25，`ConnectionStatus = Connected`）：

```
该耳机暴露的蓝牙服务：
  110C = A2DP Sink（音频接收）
  110E = AVRCP Control（媒体控制）
  → 没有 180F，即没有 GATT Battery Service
系统里也没有任何已配对的 BLE 设备
```

**结论：纯经典蓝牙（A2DP）设备在 Windows 层面拿不到电量。**
不是代码问题，也没有绕过办法：手机 App 里能看到电量是因为厂商走了私有协议，
只有自家 App 能解析。

用户四副耳机（OWS-2 / LP25 / TH11 / OPPO Enco Air Lite）**全部是经典蓝牙**，
换一副大概率同样结果。

所以按用户确认的方案降级：**只做连接状态，界面上不显示任何电量数字**。
设置页的开关说明也如实写着「不显示电量（设备不支持）」，不骗人。

### 0e.2 实现路径：为什么不用 WinRT

WinRT 的 `BluetoothDevice.FromIdAsync` 能拿到 `ConnectionStatus`，
但配合 `DeviceInformation.FindAllAsync` **一次要 300ms ~ 5 秒**；
`Get-PnpDevice` 更慢，实测单次 **5.5 秒**。
做成常驻轮询会直接吃满 CPU，完全不可行。

最终走**注册表**，一次全量只要 **65ms**：

```
HKLM\...\MMDevices\Audio\Render\{端点GUID}
  DeviceState                          1=ACTIVE 2=DISABLED 4=UNPLUGGED 8=NOTPRESENT
  Properties\{a45c254e-...},14         FriendlyName("耳机"/"扬声器")
  Properties\{840b8171-...},0          设备接口路径,**里面带蓝牙 MAC**
```

判定「蓝牙耳机端点」两条硬条件，**宁可漏报不误报**：

1. `FriendlyName` 含「耳机 / Headphone / Headset」（排除扬声器、麦克风）
2. 设备接口路径含 `bthenum`（排除有线耳机、USB 耳机、HDMI）

### 0e.3 型号名从哪来

音频端点本身只有「耳机」两个字，不带型号。

- ❌ `BTHPORT\Parameters\Devices\<mac>\FriendlyName` —— **加密的**，读出来是乱码
- ✅ `SYSTEM\CurrentControlSet\Enum\BTHENUM\<服务>\<实例>\FriendlyName` —— 明文，
  扫全表 **17ms**，按 MAC 反查即可得到 `联想thinkplus-LP25`

### 0e.4 三个实测踩到的坑

1. **同一台机器上音频端点的属性形态不一致**：有的只有 `PID 14`，有的只有 `PID 2`，
   只读一种会漏掉端点。现在两个都试。

2. **MAC 不能「找第一个 12 位十六进制串」**：设备路径里含服务 UUID，
   朴素写法会命中 `00805f9b34fb`（蓝牙基址尾巴），不是设备 MAC。
   实测第一次就踩了，表现为型号显示为空。
   正确做法：按 `& # \ _ | { }` 切段，要求**整段**恰好 12 位十六进制。

3. **`IsletHost._providers` 是按 `IslandSource` 索引的字典，一个来源只能挂一个
   Provider**：后注册的会把先注册的顶掉。
   直接给蓝牙新开一个来源注册会**把隐私提示顶掉**，表现为「开了蓝牙就看不到
   麦克风提醒」，这种 bug 极难发现。
   最终把隐私与蓝牙**合并成一个 `DeviceStatusProvider`**，两个子功能各带一个开关。

### 0e.5 自动进入 / 退出的条件

- 首次轮询只建立基线，**不提示**（避免开机就弹一条）
- 签名变化才动作：签名 = 所有激活端点的 `MAC|Friendly|IsHandsFree`，排序后拼接
- 连上 → 提示 8 秒（「🎧 型号 / 已连接 · 去蓝牙设置」）
- 断开 → 提示 20 秒（「🎧 蓝牙耳机已断开 / 已切回扬声器」）
- 轮询间隔 3 秒；注册表扫描 65~200ms，CPU 可忽略
  （实测：17 秒运行仅累计 1.08 秒 CPU，且含启动开销）

### 0e.6 实测验证

同时确认：进程稳定、日志无异常刷屏、扫描层返回
`mac=315bb0197820 | model=[联想thinkplus-LP25]`，判定完全正确。

## 0d. ✨ 2026-10-26 15:45 新功能：单应用音量面板

> 需求来源：Windows 原生把「每个应用单独调音量」藏在音量合成器里
> （右键音量图标 → 打开音量合成器），路径深、窗口小、应用重开还会重置。
> 这是清单里唯一「痛点真实 + 技术可控 + 天然契合岛形态」的一条。

### 0d.1 为什么是独立面板，而不是岛内展开

岛的资产是**单槽仲裁**：同一时刻只有一件事占主位。
音量调节是低频动作，常驻在岛里会长期占着主位，破坏这个模型。
所以做成独立窗口：岛完全不受影响，音量只在需要时出现。

入口三处：托盘菜单「应用音量…」、`Ctrl+Alt+V`、设置页「工具 → 应用音量」。

### 0d.2 数据层：`src/Islet.Sources/AudioSessionProvider.cs`

走 WASAPI：`IMMDeviceEnumerator → IMMDevice → IAudioSessionManager2 →
IAudioSessionEnumerator → IAudioSessionControl2 + ISimpleAudioVolume`。

**四个必须记住的坑（都是实测踩出来的）：**

1. **取每会话音量必须用该会话自己的 `GroupingParam`**。
   传 `Guid.Empty` 拿到的是**设备主音量** —— 所有行显示同一个值，
   而且一调就把整机音量改了。网上多数示例就是这个错误写法。

2. **`IsSystemSoundsSession()` 必须加 `[PreserveSig]`**。
   它靠**返回值**表达「是不是系统声音」（S_OK / S_FALSE），没有 out 参数。
   不加的话 CLR 把返回值当 HRESULT 吞掉，托管侧永远拿到 0，
   于是**所有会话都被误判成系统声音**。

3. **进程名不要依赖 `Process.GetProcessById`**。
   会话标识符里带着 exe 的设备路径（`\Device\HarddiskVolumeN\...\app.exe`），
   音频服务直接给出，不依赖进程枚举权限。
   实测：受限环境下 PID 反查会**全部失败**，而会话标识符仍然有效。

4. **`IAudioSessionControl2` 要把父接口方法按 vtable 顺序全部重声明**，
   不能只写自己新增的那几个。

### 0d.3 UI 层：`src/Islet.App/Views/VolumePanel.cs`

- 每行：左侧「正在发声」高亮条 ＋ 应用名 ＋ 百分比 ＋ 深色滑块 ＋ 静音键
- 拖动即时生效，不做防抖（WASAPI 调用很轻，实测无卡顿）
- 面板每秒刷新列表；**正在拖动的行跳过刷新**，否则读数会把滑块拽回去
- 关闭即释放 COM，不留悬挂引用

**三个 UI 侧的坑：**

1. **行的顺序绝不能按「是否正在播放」排**。
   最初把「正在发声的排前面」当贴心设计，结果应用一停一播整列就重排，
   用户正拖着的滑块底下换了个人。实测表现：「拖 powershell，改的却是系统声音」。
   现在只按名字排序，正在发声改用左侧高亮条表达。

2. **行里不能缓存 `AudioSession` 对象**。
   `Refresh()` 会释放上一轮的 COM 控制接口；行里若还攥着旧对象，
   写的就是已释放的接口 —— 表现为「拖了没反应，一秒后又弹回原值」。
   现在行只存 `Key`，每次写操作都通过 `Resolve(key)` 重新解析到当前这轮。

3. **自定义 Slider 模板必须用运行时 XAML**。
   `Track` 的 `DecreaseRepeatButton / Thumb / IncreaseRepeatButton` 是
   **普通 CLR 属性**，`FrameworkElementFactory.SetValue` 只接受 DependencyProperty，
   设不进去；`Track` 又不是 `IAddChild`，也不能 `AppendChild`（会抛
   `InvalidOperationException`）。只有 `XamlReader.Parse` 能直接给 CLR 属性赋值。
   注意这是**运行时** XAML，本机没有 XAML 编译器，构建流程不受影响。

### 0d.4 过滤规则：哪些会话不显示

- 状态为 Expired 的跳过
- **幽灵会话**跳过：Windows 在进程退出后不立刻删会话，而是留在 Inactive、
  exe 路径变成 `#`、PID 已不存在。实测本机就有一个，会以「未知应用」占一行。
  规则：非「正在发声」且非系统声音、且解析不出 exe 路径 → 不显示
- **浮屿自己**跳过：首次打开面板 WPF 会建一个 Islet 会话，
  自己调自己没意义，也会让用户困惑

### 0d.5 新增自检模式

```
Islet.exe --volumetest  <目录>   # 面板渲染 + 会话数
Islet.exe --volumewrite <目录>   # UI→COM 写回链路 + 刷新后是否弹回
```

`--volumewrite` 是关键：它会「建面板 → 找 Slider → 改 Value → 独立 provider 回读
→ 等一次自动刷新 → 再确认没被弹回」。只验证「面板能画出来」是不够的，
滑块能拖不等于真的写进了 WASAPI。

### 0d.6 工具

`islet/tools/AudioSessionProbe.cs`：独立控制台探针，不进构建。
可列会话、`--set <索引> <0-1>`、`--mute <索引>`，全部带**回读校验**。
排查 WASAPI 问题时先用它，比在主程序里加日志快得多。

## 0c. ✨ 2026-10-26 15:08 本轮：顶部居中修复 + 拖拽跟手 + 玻璃再调浅

### 0c.1 「顶部居中」其实早就修好了 —— 是我量错了

排查时一度以为 `Reposition()` 的 `TopCenter` 分支又坏了，实际用标尺截图复核：

- 屏幕物理分辨率 **2560×1600**（DPI 150%，逻辑 1707×1067）
- 小球窗口 `GetWindowRect` = `(1234,3)-(1327,78)`，中心 **1280.5**
- 屏幕中心 = 2560 / 2 = **1280**

**完全居中。** 之前的误判来自拿 1920 当屏宽去比对 ——
这台机器是 2560 宽。教训：**量位置前先确认真实物理分辨率**，
`GetSystemMetrics(0)` 在 DPI-unaware 进程里返回 1707，会继续误导人；
必须先 `SetThreadDpiAwarenessContext(-4)` 再取。

### 0c.2 拖拽：抓取偏移改为「相对玻璃左上角」

旧实现按「窗口左边缘跟随鼠标」拖。但窗口宽度跟内容走（卡片 400、条 300+），
而小球只占最左 26px —— 鼠标始终停在球左边，于是球永远贴着窗口左边，
窗口右边那一大片空白把屏幕右侧吃掉了。

现在 `OnDragStart` 记录的是**光标相对玻璃本体左上角的偏移**
（`_dragGrabDx/_dragGrabDy`，扣掉 `PadSide`/`PadTop` 投影留白），
`FollowCursor()` 反解出 `targetGlassLeft = cursorXDip - _dragGrabDx`，
再减留白得到窗口 Left。玻璃因此**跟手**，拖到屏幕最右也能到。

实测：从 x=1100 拖到 x=2380，窗口 `rect=(1906,3)-(2560,171)`，
正好夹紧在右边缘，日志落盘 `胶囊位置已保存`。

### 0c.3 玻璃再调浅（三档同步下移）

| 档位 | 基底 alpha（旧 → 新） | 高光 alpha（旧 → 新） |
|---|---|---|
| 深 · 沉稳 | `0x8E` → **`0x70`** | `0x5E` → **`0x54`** |
| 中 · 半透 | `0x66` → **`0x50`** | `0x52` → **`0x48`** |
| 浅 · 清透 | `0x3C` → **`0x2C`** | `0x46` → **`0x3C`** |

### 0c.4 截图里那个「圆」是抓屏假象，不是 UI bug

自检截图（`CopyFromScreen`）在条中间总有一个淡淡的圆，
一度怀疑是小球漏出来。加 `DiagnoseLayers()` 探针后确认：

```
[0] Grid vis=Visible act=0x0      ← dotLayer，_dot/_dotHalo 均 Collapsed
_dot vis=Collapsed 9x9
_dotHalo vis=Collapsed 24x24
```

**视觉树里根本没有可见的球。** 再用 WPF 自己的渲染管线
（`RenderToBitmap()`，离屏 `RenderTargetBitmap`）抓同一帧，
`offscreen-bar.png` / `offscreen-card.png` **完全干净，没有圆**。

结论：`CopyFromScreen` 抓 `WS_EX_LAYERED` 分层窗口时会拿到上一帧的陈旧内容，
那个圆是抓屏残留。**判断「画没画出来」必须走离屏渲染，不能只信屏幕截图。**

## 0. ✨ 2026-10-26 14:40 三档透明度 + 自由拖拽

> 用户反馈：①想要更透，且要能调，三档；②小球要能拖动，不能只钉在右上角
> （会挡住浏览器右上角的关闭按钮）。

### 0.1 三档透明度

三档**共用同一套玻璃层**，只改基底 alpha 与顶部高光强度，色相不变 ——
这样三档看起来是「同一块玻璃的不同密度」，而不是三种 UI。

| 档位 | 枚举 | 基底 alpha | 观感 |
|---|---|---|---|
| 深 · 沉稳 | `GlassOpacity.Deep` | `0x70` | **默认**，白雾中等，深字最稳 |
| 中 · 半透 | `GlassOpacity.Medium` | `0x50` | 能明显看到背后的色块 |
| 浅 · 清透 | `GlassOpacity.Clear` | `0x2C` | 几乎只是一层薄雾，背景内容清晰可辨 |

> ⚠️ 上表是 **0c 轮调浅之后**的最终值。0 轮最初的 `0xE0/0xA8/0x6E`
> （深色玻璃 + 白字）已被两轮推翻，别再照旧值改。

实现：`IslandWindow.BaseAlpha()` / `SpecAlpha()` 按档位返回 alpha，
`GlassBrush()` / `SpecBrush()` 用当前档位重建画刷。`SetGlassOpacity()` 只换画刷、
不动布局，所以切换是**即时**的（日志实测 `透明度已切换: Deep`）。

设置页在「外观与行为」下新增「玻璃透明度」一行，三颗药丸，点击即生效并落盘。

### 0.2 自由拖拽

**为什么不用 `DragMove()`**：它要求窗口被激活，而这个窗口是
`WS_EX_NOACTIVATE + ShowActivated=false`，调用会抛 `InvalidOperationException`，
且即便不抛也会夺焦（违反 PRD §5.4）。

自己实现：
- `MouseLeftButtonDown` 记录光标屏幕坐标 + 窗口原 Left/Top
- `MouseMove` 与一个 16ms `DispatcherTimer` **双通道**跟手（分层窗口快速拖动时
  MouseMove 会丢事件，只靠它会越拖越落后；定时器直接读 `GetCursorPos`）
- 位移 < 3 逻辑像素视为手抖 → 当作**点击**，展开卡片；否则当作**拖动**
- 拖动全程做虚拟屏幕边界夹紧，不会拖出屏幕外找不回来
- 松手后写入 `position = Free` / `freeX` / `freeY` 并立即落盘

`IslandPosition` 新增 `Free` 枚举值，**并设为默认**（固定角落挡浏览器按钮是用户明确抱怨的问题）。
`Reposition()` 在 `Free` 时直接用保存坐标；首次启动 `freeX/freeY` 为 NaN 时回落到右上角。

设置页「停靠位置」从 3 个选项变成 4 个，`自由拖动` 排第一。

## 5. 核心架构：评分与抢占

```
score = BaseWeight[来源] + Urgency×0.40 + Actionability×0.30
      + Pinned(200) + 新鲜加成(≤10，60 秒衰减) - 冷却惩罚(25)
```

**BaseWeight**：Meeting 80 / Privacy 75 / Health 70 / Timer 55 / Progress 50 / Clipboard 45 / Media 10

抢占规则：
- **硬抢占**：`HardPreempt=true` 无视分差（会议临场、电量告急、计时到点、隐私占用）
- **软抢占**：新分 > 当前分 + 15（滞回带防抖动）
- **不抢占**：`Pinned` 或用户展开卡片期间（`SuspendPreemption()`）
- **退场**：TTL 到期 → 队列补位 → 回落媒体（地板态）→ 隐藏点

## 2026-10-27 · 岛内应用音量 + 网易云上岛

### 背景
用户反馈「网易云不放岛上、摄像头麦克风正常、把单独应用音量调节做到岛上」。

### 三个真实缺陷（都已修）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 网易云正在播放，岛上没有任何反应 | ① `MediaProvider` 只走 SMTC，而**网易云不注册 SMTC**（实测播放中会话数为 0）；② 上一轮新建的 `NowPlayingProvider` **从未注册**，是死代码 | `MediaProvider` 增加「音频会话回落」：SMTC 拿不到会话时，改看 WASAPI `State==1`（确实在出声）。用同一个 `IslandSource.Media` 键，避免两个 Provider 互顶。`NowPlayingProvider` 收敛为纯判据工具类 |
| 2 | 拖音量滑块时整个岛被拖跑 | 窗口级 `MouseLeftButtonDown` 抢走了滑块的按下事件 | `OnDragStart` 里判断是否按在混音器内部（`IsInside`），是则让路给滑块 |
| 3 | 内存涨到 2.9 GB、线程 3.6 万 | `Refresh()` 里 `ctl` / `ctl2` / `sessionEnum` 三处 COM 引用**从未 Release**；叠加高频轮询后按「会话数 × 次数」爆炸 | 枚举循环内 `finally` 释放 `ctl2`/`ctl2`/`sessionEnum`；缓存 `_enumerator` 不再每轮新建；轮询 2s → 30s |

### 关键实测数据

```
修复前：线程 36000+ / 内存 2911 MB / 系统音频会话 9963
修复后：线程 15-19  / 内存 ~98 MB  / 会话数 90 秒仅 +4（与 30s 轮询严格对应）
停止 Islet 后会话数立即回落到 2 → 证明增长确由本进程枚举引起，非系统问题
```

### 交互形态
- 有应用出声 → 点岛直接展开「应用音量」面板（网易云音乐 / 100% / 滑块 / 静音）
- 全部停下 → 自动回落到普通卡片或隐藏点
- 展开时**立即重新枚举一次**，所以即使收起态轮询是 30 秒，点开仍是即时的

### 为什么轮询是 30 秒（性能红线，别调快）
WASAPI 的会话枚举本身会让音频引擎留下会话对象，客户端释放 COM 引用也回收不了。
2 秒轮询一小时能攒近两千个僵尸会话，把音量面板拖到卡顿。30 秒把它压到 1/15，
且 Islet 退出后这些会话全部消失，不会残留到下次开机。

## 2026-10-27 · 小圆环定位修复（锚点重做）

### 用户反馈的三个现象（同一个根因）
1. 鼠标碰到小圆环就自动弹开矩形区域
2. 拖动矩形时不能超出屏幕，且**收起后小圆环跑到矩形左侧**
3. 音乐播放后变成的小矩形（条形态）也有同样问题

### 根因
窗口位置一直按**窗口左上角**保存和计算，而窗口宽度随形态剧烈变化：

```
圆环 62px  →  条 ~430px  →  卡片 654px
```

展开时窗口向右长，撞到屏幕右边缘被夹紧后整体被推左；
收起时窗口缩回，但左上角已经是「被推左之后」的值，于是圆环永久偏到左边。
用户拖到靠右位置后，每展开一次球就往左漂一点 —— 这就是「球不能自由移动」的真相。

### 修法
1. **锚点改为「小圆环中心」**（`FreeX/FreeY` 语义变更）
2. 新增 `PlaceAroundAnchor()`：展开时优先向空间更大的一侧生长
   - 右边放得下 → 向右展开（圆环在左端）
   - 右边不够 → 向左展开（圆环在右端），不再硬夹紧推走
   - 两侧都不够才做最小夹紧
3. 拖动也锚定圆环中心，`FollowCursor` 直接更新锚点
4. **圆环态不再悬停展开**，改为点击展开（`MouseEnter` 里判断 `_dot.Visibility`）

### 实机验证（两种场景，逐像素比对）

**场景 A：屏幕中间**
```
拖动后收起  1169,781,1262,856   (93x75)   圆环中心 (1200,800)
展开       1169,781,1823,949   (654x168)  ← Left 未变
收起       1169,781,1262,856   (93x75)    ← 完全回到原位
```

**场景 B：贴屏幕右边缘（原缺陷最严苛场景）**
```
收起       2434,206,2527,281   (93x75)   圆环中心 (2465,225)
展开       1873,206,2527,374   (654x168)  ← 向左生长，右边缘 2527 不变
收起       2434,206,2527,281   (93x75)    ← 完全回到原位
```

关键点：展开时**右边缘 2527 三次一致**，说明面板是从圆环向左侧铺开的，
圆环本身一格没动 —— 这正是用户要的「球钉在那儿」。

### 兼容性说明
旧 `settings.ini` 里 `freeX/freeY` 存的是窗口左上角，新语义是圆环中心，
首次启动会有约 31px 的水平偏移（仍在屏幕内），拖动一次即自动纠正为正确值。

## 2026-10-27 · 应用图标

### 做了什么
给浮屿做了一套完整图标，并接到三个地方：**exe 资源**、**托盘**、**快捷方式/资源管理器**。

- `islet/tools/IcoGen/IcoGen.cs`：用 GDI+ 代码画图并写出 ICO。

- `TrayIcon.cs` 改为从 exe / 同目录 `islet.ico` 取图标，替换原来程序化画的白色圆点。

2. **函数内取不到脚本级 `$root`**（这个脚本里实测为 `$null`），

## 2026-10-27 · 修复：岛上音量不生效 + 插耳机后岛上空白

两个症状，两个独立原因，但都落在 `AudioSessionProvider` 里。

### 一、音量滑块「看着在动，实际没作用」

**根因**：取每个应用的音量控制时用错了 API 参数。

```
旧代码：_manager.GetSimpleAudioVolume(ref grouping, 0, out vol)
```

`GetSimpleAudioVolume` 的第一个参数是**会话 GUID**（应用创建会话时用的那个），
而代码传进去的是 `IAudioSessionControl::GetGroupingParam()` 返回的**分组参数**。
两者不是一回事。传错的结果是：每次调用都拿到一个「新造的、与会话无关」的音量对象，
写进去 S_OK、读回来也是你写的值，但跟应用本身毫无关系。

实测证据（`islet/tools/VolDiag`）：

```
QI 路径写 30%  -> 回读 30.0%        ← 真的改了
同一时刻 GetSimpleAudioVolume(grouping) -> 回读 100.0%   ← 完全无关
```

**修法**：对会话控件做 QI 拿 `ISimpleAudioVolume`：

```csharp
ISimpleAudioVolume vol = ctl as ISimpleAudioVolume;
```

### 二、改完 QI 之后踩到的 RCW 分离坑（关键）

改成 QI 后第一次跑，写入报：

```
SetMasterVolume 异常: COM 对象与其基础 RCW 分开后就不能再使用。
```

**原因**：`ctl as ISimpleAudioVolume` 返回的接口与 `ctl` 是**同一个 RCW**
（.NET 按 COM 标识共用包装）。而枚举循环的 `finally` 里又会把 `ctl` / `ctl2`
`Marshal.ReleaseComObject` 掉 —— RCW 计数归零、被「分离」，
刚存进 `s.Control` 的接口立刻失效。

之前用 `GetSimpleAudioVolume` 拿到的是**另一个** COM 对象，所以这个坑一直没暴露。

**修法**：`ReadOne` 增加 `out bool keepsCtl`。会话把从 `ctl` QI 出来的接口留在
`s.Control` 上时，循环里**不释放 ctl**，交给 `ReleaseSessionControls()` 统一释放一次
（同一个 RCW 只释放一次）。顺带把 `finally` 里「ctl2 和 ctl 各释放一次」改成只释放一次
——它们本来就是同一个 RCW，重复释放会抛异常（虽被 catch 吞掉，但语义是错的）。

**教训**：COM 对象的引用计数与「.NET 接口强转」不是一回事。
把一个 RCW 派的接口存起来长期用，就不能再对这个 RCW 的任何一个接口调 `ReleaseComObject`。

### 三、插耳机后岛上没响应 / 空白

**根因**：`Refresh()` 里写着注释「复用已有的 manager；设备变了就重建」，
但代码只有 `if (_manager == null)` —— **根本没有设备变化检测**。

manager 是 `Activate` 自某个**具体设备**的。插耳机后默认设备切走，旧 manager 仍绑旧设备：

- 枚举出来的是旧设备的会话 → 岛上「谁在出声」空白
- 音量写进旧设备的会话 → 应用音量不动

**修法**：

1. `IMMDevice` 补上 `GetId()`（vtable 第 3 槽，原来占位成 `NotImpl2`）。
2. `Refresh()` 取当前默认设备 ID，与 `_deviceId` 比较，不同就 `ReleaseManager()` 后重建。
3. 新增 `DeviceChangedLastRefresh` / `DeviceId` 属性；`IslandWindow.RefreshAudio()`
   在检测到切换时记一条日志「默认播放设备已切换: …」，方便以后定位这类问题。

### 四、另外：`bluetooth = false`

`settings.ini` 里蓝牙数据源是关的，所以**连耳机根本没有岛内提示**。
本次改成 `bluetooth = true`（用户配置变更，原始值备份在 `.backup/20261027-2030/`）。

## 2026-10-27 · 补充：有线耳机（实测结论）

### 这台机器的音频拓扑（实测，别再猜）

两个「启用」的播放端点，名字**都叫「扬声器」**，靠名字区分不了：

| 端点 ID 前缀 | 真实设备 | 用途 |
|---|---|---|
| `24e21077…` | Realtek(R) Audio | 板载声卡 |
| `8043c22c…` | 适用于 USB 音频的英特尔® 智音技术 | **有线耳机走这个** |

关键实测（拔掉耳机时连续采样注册表 `DeviceState`）：

```
21:14:30  24e21077/扬声器=1 | 8043c22c/扬声器=1     ← 两个都活动（耳机插着）
21:15:46  24e21077/扬声器=1                         ← 耳机拔掉，8043c22c 掉出
21:16:12  24e21077/扬声器=1 | 8043c22c/扬声器=4     ← 8043c22c 变成「未插入」
```

结论：
1. **Windows 确实感知插拔**（端点掉到 `DeviceState=4`），所以软件能检测。
2. 耳机插着时，默认端点**就是** `8043c22c`。拔掉后 Windows 会切走默认端点。
3. 因此「插耳机后岛上空白」的根因就是本文件上一节那个「没有设备变化检测」的 bug
   —— 旧 manager 绑在旧端点上，枚举出来是空列表。修复后已实测正常（见下）。

### 已验证（耳机插着时）

- 岛上混音面板正常显示「网易云音乐 81%」（不是空白）
- 在岛上拖到 49%，独立探针读回**真实音量 49%** ✓

### 新增：设备变化推送监听（`AudioDeviceWatcher`）

媒体条原本 30 秒轮询一次（频率是性能红线，不能调快）。
插拔耳机后最多要等半分钟岛上才更新，体感就是「没反应」。

现在用 `IMMNotificationClient`（`RegisterEndpointNotificationCallback`）接系统推送：

- 设备切换瞬间 → `MediaProvider.OnAudioDeviceChanged()` → 立即 `Poll()`
- **不枚举会话**，成本接近零，不需要动轮询频率
- 注册失败只会静默退回轮询，不影响主流程
- 启动日志会写明结果：`音频设备变更监听: 已注册（插拔耳机即时刷新）` / `注册失败，退回 30 秒轮询`

实现上要留意的两点（都踩过/防过）：
- 实现 ComImport 接口的托管类会被 CLR 包成 CCW，**必须保住强引用**，否则被 GC 后回调静默断掉
- 回调在系统线程上，`Poll` 加了 `Interlocked` 互斥，避免定时器和回调同时枚举会话

### 未实测

设备切换后岛上**具体多少毫秒**更新，没有量出来（用户跳过了这一步）。
`islet/tools/WinWatch` 就是为此写的：打印岛窗口尺寸变化的时间戳（条↔圆点即内容变了）。

用法：
```
build\WinWatch.exe Islet 100 out.log
```
跑起来后拔插耳机，看日志里尺寸变化的时间点即可。

## 2026-11-01 · 修复：贴右边缘展开时「瞬移」

### 现象
岛拖到屏幕右侧、靠近右边界后，展开成条/卡片时**整块玻璃突然向左跳一大段**，
像瞬移。收起又能回来，但展开那一下很难看。

### 根因（几何必然，不是坐标算错）
旧 `PlaceAroundAnchor` 在「右边放不下」时走「向左生长」分支：让**窗口右边缘**
对齐锚点。但圆环恒在窗口**左端**，于是圆环被推到

    anchorX - w2 + PadSide + DotSize/2

实测在 2560 宽的屏上整整左跳 **359px**。那个分支的本意是「保住圆环位置」，
结果反而把它推得最远 —— 逻辑反了。

### 修法
1. **右边放不下就贴住右边缘**，不再整体左移到锚点右侧。
   `winLeft = vRight - w2`，并夹紧到不越左边界。
2. 垂直方向同样处理（`winTop = vBottom - h2`）。
3. 新增 `AnimateTo(left, top)`：位移超过 1px 时做 140~260ms 的 EaseOut 过渡，
   距离越长给的时间略长但封顶，避免拖动时拖尾。

**关键取舍**：动画的是 `Left/Top`（窗口位置），**不是宽高**。
位置和布局系统完全解耦，不会重蹈上一轮「动画 Width 被 SizeToContent 忽略、
且让测量失效导致窗口宽度算成 1914px」的覆辙。

## 2026-11-01 · 性能：播放响应 + 拖动卡顿

### 一、播放/停止响应慢（最多 30 秒）

**根因**：`_timer = new Timer(Poll, null, 2000, 30000)` —— 30 秒才轮询一次。

这个 30 秒是历史包袱：早先实测「2 秒轮询一小时攒近两千个僵尸音频会话」。
但那条结论的前提是**每次 new 一个 AudioSessionProvider**，每次都 `device.Activate`
出新 manager，引擎侧才会不断留下对象。

现在 provider 复用 `_manager` 和 `_enumerator`，前提已经不成立。

**实测验证**（`islet/tools/PollCost`）：

```
同一个 provider 连续 Refresh 600 次
  成功 600，总耗时 1129ms，单次平均 1.881ms
  系统会话总数：4 → 4，增量 0
```

**改动**：
- 轮询 `30000` → `2000`（2 秒）
- `FallbackHold`（停止后挂多久才撤）`3s` → `1.2s`
  —— 原来停止播放后要等「轮询 + 3 秒」才消失，体感很慢

**实测资源**（连续运行 60 秒）：
```
线程 15，内存 99.5MB，CPU 累计 1.16 秒（≈1.9%）
系统会话总数 3 次采样均为 4，无累积
```

**重要前提**：如果以后改了 `AudioSessionProvider` 的生命周期策略
（比如又变成每次 new），**必须重新跑 `PollCost` 验证**，否则会话泄漏会回来。

### 二、拖动卡顿

**根因**：`FollowCursor` 每 16ms 跑一次，而每次都在做**系统级查询**：

```csharp
SystemParameters.VirtualScreenLeft/Top/Width/Height   // 每次跨进程问窗口管理器
ActualWidth / ActualHeight                            // 布局脏时会触发一次布局
```

这些值在拖动过程中根本不变，每帧重算纯属浪费。

**改动**：
1. 新增 `FillDragCache()`：在 `OnDragStart` 里量一次，`OnDragEnd` 时失效。
   `FollowCursor` 全程读缓存。
2. 拖动定时器优先级 `Background` → `Render`
   —— 默认优先级会和布局、数据绑定抢时间片，表现为一顿一顿。

`.backup\20261101-2230\`：`MediaProvider.cs.bak` / `IslandWindow.cs.bak` / `NowPlayingProvider.cs.bak`
文档备份 `.bak11`

**注意**：轮询改回 30 秒只需改 `MediaProvider.Attach` 里那一行；
拖动缓存若出问题，删掉 `FillDragCache` 调用、把 `FollowCursor` 里的缓存变量
换回原来的 `ActualWidth/SystemParameters` 即可。

## 2026-11-01 · 拖动第二轮：顿挫的真正根因 + 任意空白区可拖

上一轮（见上节「二、拖动卡顿」）只做了「缓存参数 + 提高定时器优先级」，
用户实测反馈**还是顿**，而且「只有边缘能拖」。这轮找到了两个真正的根因。

### 一、顿挫根因：每帧重启一次 EaseOut 动画

上一轮漏掉了一件事：`FollowCursor` → `PlaceAroundAnchor` → `AnimateTo`。
也就是说**拖动过程中每 16ms 就启动一个新的 140~260ms `CubicEase.EaseOut` 动画**。

EaseOut 是「起步快、收尾慢」。每帧重启等于每帧把「已经走了多远」清零，
窗口永远只走到目标的一小段就被新目标重置 ——
表现为**拖得越快落得越远，像拖着一根橡皮筋**。这才是顿挫感的真正来源，
和渲染、阴影、分层窗口、参数查询都无关。

**修法**：给 `PlaceAroundAnchor` / `AnimateTo` 加 `bool animate` 参数。
拖动时（`FollowCursor`）传 `false`，直接 `Left = x; Top = y`。
形态切换导致的被动位移（展开/收起贴边）仍然走动画 —— 那种场景用户没在拖，
平滑过渡是加分项。

顺带两个小优化：
- `FillDragCache` 一并缓存 DPI 缩放比（`PresentationSource.FromVisual` 不便宜）；
- `FollowCursor` 里光标坐标没变就直接 return，用户手停下来时不再空转。

### 二、只有边缘能拖：订阅挂错了元素

上一轮写的是 `_content.PreviewMouseLeftButtonDown += OnDragStart;`。
**`_content` 根本不在点击路由上**：

```
玻璃的 Background 画在 _shell（Border）上
空白处命中的就是 _shell 本身
路由：_shell → shellHost → _root → Window
```

`_content` 是 `_shellInner` 的子级、`_shell` 的**后代**，不在那条路由上，
所以按在空白玻璃上时它一次都不会触发。只有按在圆角边缘（落在窗口透明底上）
时才走另一条路，看起来就像「只有边缘能拖」。

**修法**：改成窗口级 `PreviewMouseLeftButtonDown += OnDragStart`。
Preview 是整条路由的起点，无论命中 `_shell`、`_bar` 还是 `TextBlock`，都先经过它。

代价：按钮/滑块也会先经过它，所以新增 `IsInteractiveUnder()`，
沿 `OriginalSource` 向上找 `ButtonBase` / `RangeBase` / `Thumb` / `TextBoxBase` /
`Selector` / `PasswordBox`，命中就让路。
（上一版只排除了混音器，卡片上的「暂停 / 上一首 / 下一首」按钮一按就会被
`CaptureMouse` 抢走 —— 这是把入口提到窗口级后必然要补的一步。）

同时删掉了冒泡阶段的 `MouseLeftButtonDown += OnDragStart`，
现在按下入口**只有 Preview 一条**。

## 2026-11-01 · 播放/停止第三轮：从「拉」改成「推」

用户前两轮反馈的都是「响应慢」。前两轮分别把轮询从 30s → 2s、再到
缓存参数，都只让数字好看了一点，**体感没变**。这轮才找对方向。

### 一、为什么前两轮没用：瓶颈不是开销，是「拉」这个模型

先量化了开销（`islet/tools/PollCost`）：

```
同一个 provider 连续 Refresh 600 次 → 总耗时 1216ms，单次 2.03ms
系统会话总数 4 → 4，增量 0
```

单次 2 毫秒，**轮询本身根本不贵**。那问题只能是：

> 无论轮询多快，一次状态变化**最坏都要等满一个周期**才被发现。

2 秒周期 + 1.2 秒 `FallbackHold` = 最坏 3.2 秒才撤条。用户按了停止，
岛还挂着三秒，当然是「慢」。再压低轮询只是拿 CPU 换感觉，治不了根。

### 二、改法：把状态变化变成系统主动通知

WASAPI 有两层通知，**必须用对**：

| 接口 | 挂在谁身上 | 什么时候回调 | 对本需求有用吗 |
| --- | --- | --- | --- |
| `IAudioSessionNotification::OnSessionCreated` | `IAudioSessionManager2` | **新会话被创建** | ❌ 几乎没用 |
| `IAudioSessionEvents::OnStateChanged` | 每个 `IAudioSessionControl` | 会话 Active↔Inactive | ✅ 就是它 |

第一版我挂的是 `IAudioSessionNotification`，实测跑了两轮都是「推送回调 0 次」。

原因是：**播放器暂停再播放时，会话对象一直存在**，只是 `State` 从 1 变 0、
再从 0 变 1，**不会创建新会话**，所以 `OnSessionCreated` 永远不触发。
（这个接口是给「应用第一次出声」用的，正是系统音量合成器加新行的时机。）

换成 `IAudioSessionEvents` 之后，它正是音量合成器刷新「应用正在发声」那行用的
同一个回调，播放/暂停/停止都会走 `OnStateChanged`。

**几个必须注意的细节**（都是实测踩出来的）：

1. `RegisterAudioSessionNotification` 属于 **`IAudioSessionControl`**，不是
   `...Control2`。必须用 `ctl` 调。用 `ctl2` 的话 vtable 槽位错开，
   会调到隔壁方法上 —— 表现为「注册返回 0 但永远收不到回调」，极难查。
2. `IAudioSessionControl2` 继承了父接口，那两个槽位也得保留，否则新增方法整体错位。
3. 回调**只发信号，不做任何 COM 调用**。它跑在音频服务的线程上，
   在里面枚举会话会直接拖住音频引擎。
4. 回调节奏会连发多个，用 `Interlocked` 防抖合并成一次刷新；
   派到线程池并 `Sleep(60)`，等会话真的进入 Active 再读
   （实测 `OnSessionCreated` 触发时会话状态偶尔还是 Inactive）。

### 三、顺手修掉的两个真 bug

**bug 1：每 800ms 泄漏一个 COM 引用。**

`Refresh` 每轮都新建 `AudioSession` 并持有本轮的 `ctl`。第一版复用回调时写的是：

```csharp
s.Events = existing.Events;
s.Ctl = ctl;
keepsCtl = true;      // ← 于是 finally 不释放 ctl
```

`s.Events` 非空，`ReleaseSessionControls` 就跳过释放 `s.Control`，
于是**每轮泄漏一个 ctl**。改成：把本轮易变字段合并进旧对象，
然后立刻释放本轮 ctl（`s.Control` 与 `s.Ctl` 是同一个 RCW，只释放一次）。

**bug 2：会话数翻倍 4 → 8。**

复用分支里 `_sessions.Add(existing)`，而调用方拿到返回值后还会 `_sessions.Add(s)`
—— 一条会话算两条。实测 `PollCost` 打出「最后一次会话数 = 8」，
界面上会显示成「网易云音乐 等 2 个应用」。删掉分支里那次 Add 即可。

> 这两个都是「看起来能跑、数字也差不多」的 bug，靠 `PollCost` 的
> 「最后一次会话数 / 系统会话总数增量」两行才抓出来。**改 provider 必跑它。**

### 四、为什么还留着轮询

`OnStateChanged` 覆盖了播放/暂停/停止，但还有兜底需求：
设备切换、会话过期、以及**注册失败**的机器。所以：

- 轮询间隔 `2000ms → 800ms`（单次 2ms，这个频率毫无压力）；
- `FallbackHold 1.2s → 450ms`（有了推送，这段纯是撤条延迟，只需盖住切歌抖动）。

理论最坏延迟：推送路径 **≈ 60~100ms**；兜底路径 800 + 450 ≈ 1.25s。

### 五、验证

```
系统会话总数 4 → 4，增量 0

PASS=33 FAIL=0
```

### ⚠️ 本机无法注入输入（重要）

想主动触发播放/暂停来测端到端延迟，试了三条路都不通：

- `SendInput`：**返回 1**，但事件没送达（它只入队，不保证送达）；
- `SetCursorPos` / `OpenInputDesktop`：都返回 `err=87`，
  说明本进程跑在**不可交互的窗口站/桌面**；
- `keybd_event` 发媒体键：同样无效；
- `desktop_control` 的 `key` 动作不支持媒体键。

所以**播放/暂停的端到端延迟只能由用户在真实桌面手动验证**。
代码层面的证据是充分的（推送注册成功 + 日志有发布记录 + 压力测试无泄漏），
但「按下去多久有反应」这个数字本机测不出来。

```
错误偏移: 0x6b477
```

`AUDIOSES.DLL` 是音频会话服务，说明是我们注册的回调在音频引擎线程里崩了。

```csharp
ISimpleAudioVolume vol = ctl as ISimpleAudioVolume;   // 同一个 RCW

...

```

> 教训：**回调路径无法本地验证时，不要上线。**
> 「注册返回 0」不等于「回调安全」；真正的验证必须是「事件真的发生过」。

## 2026-11-02 · ✅ 修好：「暂停要二十多秒才变回小球」

上一节说「这个问题没解决，但也不再崩了」。这一节把它解决了 ——
**而且没碰任何 COM 回调**，所以不存在崩溃风险。

### 一、根因：`State` 这个判据本身就是错的

先别再猜，直接量。`islet/tools/PeakProbe` 同时读 `State` 和音量峰值
（`IAudioMeterInformation::GetPeakValue`），暂停瞬间的输出是：

```
18:35:26.859   网易云音乐  State=1  Peak=0.094
18:35:27.018   网易云音乐  State=1  Peak=0.000   ← 暂停，峰值立刻归零
18:35:46.837   网易云音乐  State=0  Peak=0.000   ← 19.8 秒后 State 才跟上
```

**峰值在暂停那一刻就归零，而 `State` 整整晚了 19.8 秒。**

原因是网易云暂停时**不关闭音频流**，只是不再往里写数据。
音频引擎认为流还活着，于是会话继续报 `State = 1 (Active)`，
直到长时间没数据才回收 —— 那才是 20 秒的来源。

之前几轮一直盯着「轮询周期」「FallbackHold」调，方向全错：
哪怕轮询每秒 100 次，读到的 `State` 也还是 1。

### 二、修法：判据换成峰值

`NowPlayingProvider.FindPlaying()` 里：

```csharp
// 旧：if (s.State != 1) continue;
if (s.State == 2) continue;        // 2 = Expired，会话已失效
if (s.Peak <= 0.0005f) continue;   // 没在出声
```

阈值 `0.0005` 的依据是实测数据：播放时峰值在 **0.02 ~ 0.53** 之间波动，
暂停后是**精确的 0.000**。取这个值既能盖住极安静的段落，又不会被浮点噪声骗到。

配套两处：

- `FallbackHold` 1.2s → **0.45s**（判据准了，这段纯是防抖）
- 轮询 2s → **0.5s**（单次 1.56ms，每秒 2 次约 0.4% 单核）

**结果：暂停后约 0.5 秒岛收回**，用户确认「半秒到一秒内，明显快了」。

### 三、这次为什么不会崩（和上一轮的关键区别）

上一轮崩在「同一个 RCW 被两个字段持有、只 Release 一次」。

这次读峰值是这么写的：

```csharp
IAudioMeterInformation meter = ctl as IAudioMeterInformation;   // 局部变量
float peak;
if (meter.GetPeakValue(out peak) == 0) s.Peak = peak;
// meter 出作用域，不保存、不 Release
```

**只 QI 到局部变量，读完即弃，绝不挂到 `AudioSession` 上。**
所以它不参与任何引用计数，也就不可能重演那次闪退。

> 判据：WASAPI 里凡是「只想读一个值」的接口（峰值、通道数），
> 都该用局部变量读完就走；**只有需要长期持有的才放进对象字段**，
> 而一旦放进去，就必须想清楚谁负责 Release。

### 四、验证

```

600 次 Refresh：单次 1.560ms，会话数 2 → 2，增量 0
部署后：89.2MB / CPU 1.22s / 零 ERROR

  18:38:19.903  发布媒体事件
```

## 2026-11-05 · ✨ 新功能：临时存放站（文件暂存 / 拖出）

用户需求：把文件暂存到浮屿，随时从岛上拖出来，放进不同文件夹，
或直接拖进聊天框发给好友 / agent。

### 一、方案与取舍（用户确认过的四点）

| 选择项 | 结论 |
| --- | --- |
| 存什么 | **复制副本**到 `%LOCALAPPDATA%\Islet\stash\`，原文件自始至终不动 |
| 怎么放进来 | **直接把文件拖到岛上**（岛是拖入入口） |
| 拖出去 | **移动/剪切**语义：拖出成功后把条目从收纳站移除 |
| 重启后 | **清空** |

原文件从没进过收纳站，只是被复制了一份进去。删除是不可逆操作，不做。

还有一个 Windows 固有约束：拖放效果由**接收方**决定。
`DragDrop.DoDragDrop` 传 `Copy | Move`，资源管理器默认 Copy（按 Shift 才 Move），
聊天框一般只收 Copy。代码只在返回 `Move` 时移除条目 —— 这符合标准语义，
也不会因为「发给好友」而误删副本。

**`StashPanel` 是独立小窗**，不是 `IslandWindow` 的新形态。

理由：`VolumePanel` 已证明这个模式在本项目成熟可靠；而 `IslandWindow` 的形态系统
（`SizeToContent` / 拖动 / `AnimateTo` 位移动画）历史坑极多（见前面几节：
1914px 宽度、闪退、跟手性），往里再加一种形态风险远大于收益。

岛只承担两件事：
- **拖入入口**：`AllowDrop = true` + `DragDrop`/`DragEnter`/`DragOver` 接收 `FileDrop`，
  通过 `FilesDropped` 事件把路径交给宿主
- **数量角标**：`_root` 右上角一个红色数字徽章，`IsHitTestVisible=false`，
  不参与命中测试，不影响窗口拖动，也不影响 `SizeToContent` 测量

拆成四条硬约束：

1. 中转区在**同一块玻璃内部**右侧，不是第二个窗口；
2. 它与音乐播放等形态**共存**，不互相替换、不分成两个界面；
3. 没有文件时 UI **与之前完全一致**（宽度逐像素相同）；
4. 有文件时玻璃才**向外延伸**。

### 二、怎么做的（`IslandWindow.cs`）

`_content` 从「四种形态平铺」改成**两列**：

```
_shellInner
  _spec / _innerRim
  _content (Grid, 两列)
    [0]  *    _mainHost   ← dotLayer / _bar / _card / _mixer 原样搬进来
    [1]  Auto _stashBox   ← 中转区方框（176 宽，默认 Collapsed）
```

关键点：**右列 Collapsed 时宽度为 0**，所以第 3 条约束不需要任何开关，
它是布局的自然结果。实测证据（`--selftest` 报告原文）：

```

_stashBox vis=Visible act=176x158.33 rows=3 extra=188
shell min/max=588/588
```

436 是加功能前的卡片窗口宽度；188 = 方框 176 + 右边距 12。

尺寸规则集中到 `ApplyMetrics()` —— **全类唯一**设置 `_shell.Width/Height/Min/MaxWidth` 的地方：

| 形态 | 宽度 | 高度 |
| --- | --- | --- |
| Dot | 固定 `DotSize` | 固定 `DotSize` |
| Bar | `NaN`（内容决定）+ 中转区那一列 | 中转区可见时 `NaN`，否则 `BarHeight` |
| Card / Mixer | `MinWidth = MaxWidth = CardWidth + StashExtra()` | `NaN` |

为什么必须集中：卡片/混音器的宽度只能夹在 `[Min,Max]` 区间里
（`SizeToContent` 把 `Width` 当建议值，实测 400 会被撑到 436），而条是自动宽度。
这套规则原本分散在四个 `Show*` 里，每加一条就要改四处，漏一处就是「内容被裁掉」。

**条形态的高度必须放开**：条本身只有 38，装不下 158 高的方框。所以中转区可见时

否则玻璃变高后它们会垂直居中，看起来像浮在玻璃中间。
（中转区不可见时行高恰好等于它们自身高度，Top 与 Stretch 完全等价，不影响旧外观。）

## 2026-11-05（补）· 悬停展开加 500ms 延迟

### 现象

媒体播放时岛是条形态。用户想把它推到屏幕最右，但**鼠标一碰到条就展开成 400 宽的大框**，
而大框不能越过屏幕右边（窗口夹在屏内），于是「推到最右」永远做不到 ——
手一碰它就先变大了，这时候再往右拖已经是「把大框往右推」，没有空间。

### 改法（`IslandWindow.cs`）

去掉 `MouseEnter → SetExpanded(true)` 的直接调用，换成 500ms 倒计时：

```
MouseEnter  → StartHoverExpand()     起 500ms 计时（圆环态 / 已展开 → 不起）
计时到点    → 再确认 IsMouseOver && !_dragging && !_stashDragging → SetExpanded(true)
MouseDown   → CancelHoverExpand()     （OnDragStart 第一行，按下即作废）
MouseLeave  → CancelHoverExpand() + ScheduleCollapse()（原有 400ms 收起）
```

三种意图因此分开：

| 意图 | 行为 |
|---|---|
| 路过 | 不到半秒就走了 → 不展开 |
| 想拖它 | 按下鼠标立刻取消倒计时 → **整个拖动过程保持条形态**，能贴到屏幕最右 |
| 想看 | 停在上面不动 → 半秒后展开 |
| 点一下 | 仍立即展开（`OnDragEnd` 里位移 <3px 算点击，原逻辑没变） |

两个顺带修的：

- 倒计时用 `DispatcherPriority.Background`：这是「没人操作时才会发生的事」，
  不能和渲染、拖动跟随抢时间片。
- `ScheduleCollapse` 的 tick 里补了 `if (_dragging) return;`。原来只挡了
  `_stashDragging`，拖动中万一有 MouseLeave 排了收起任务，`Show*` 里的
  `UpdateLayout()` 会在 16ms 的跟随节奏里插一次强制布局 —— 又是一顿。

### 参数

`HoverExpandDelayMs = 500`（`IslandWindow` 里，靠近 `ScheduleCollapse`）。
嫌慢/嫌快改这一个常量；`0` 就等于恢复成「一碰就展开」。

```

```

## 2026-11-05（补二）· 拖动掉帧：根因与优化

### 一、先量，不猜

新工具 `islet/tools/DragCost`（纯 ASCII，独立编译，不进正式构建）：

```
csc /target:exe /out:build\tools\DragCost.exe + WPF 四个引用  islet\tools\DragCost\DragCost.cs
build\tools\DragCost.exe 2000
```

它量三件事：A = `Window.Left/Top` 赋值（等于两次 SetWindowPos）、
B = 单次 `SetWindowPos`、C = `BeginAnimation(null) ×2 + Left/Top`（就是
`AnimateTo(animate:false)` 当时干的活）。窗口做成和岛一样的分层窗 + 同样参数的
`DropShadowEffect`（BlurRadius 26）。

**实测（150% DPI，窗口 430×62，各 200 次平均）**

| 变体 | A Left/Top | B SetWindowPos | C BeginAnimation+A |
| --- | --- | --- | --- |
| 分层 + 投影（接近岛） | **0.911 ms** | **0.516 ms** | 0.725 ms |
| 分层无投影 | 1.308 ms | 0.856 ms | 0.984 ms |
| 非分层 | 1.872 ms | 0.839 ms | 2.197 ms |

两个结论：

1. **投影和分层窗口都不是问题**（分层+投影反而最快），所以不需要为了性能
   去关投影或放弃圆形玻璃。
2. 一次「搬窗」0.5~0.9ms，占 16.6ms 帧预算的 3~5.5%。**单次不致命**。

### 二、真正的根因：一帧搬了十几次窗

`FollowCursor` 原来有**两个**调用入口：16ms 定时器 **和** `MouseMove`。

高回报率鼠标（1000Hz）一秒发 1000 个 MouseMove，一个 16ms 帧里就是十几次；
每次都要搬一次窗（0.5~0.9ms）→ **一帧光搬窗就花掉 7~14ms**，帧预算直接爆。
表现就是「拖动有点掉帧」，而且**鼠标动得越快越明显** —— 与用户描述一致。

定时器本来就是为了兜住「MouseMove 会丢事件」而存在的，再挂一个 MouseMove
等于把兜底方案用成了加速器。

### 三、改了四处（`IslandWindow.cs` / `NativeMethods.cs`）

1. **删掉 `MouseMove += OnDragMove`**（连带删掉 `OnDragMove` 方法）。
   一帧最多搬一次窗，跟手延迟上限 16ms = 一帧，肉眼无差别。
2. **一帧只调一次 `SetWindowPos`**。新增 `MoveWindowRaw(left, top)`：
   逻辑像素 × 缓存 DPI → `SetWindowPos(SWP_NOSIZE|NOZORDER|NOACTIVATE|NOSENDCHANGING)`。
   `AnimateTo(animate:false)` 在拖动期间走这条路（0.52ms，而不是 0.91~0.73ms 的
   `BeginAnimation + 两个 DP`）。
3. **拖动期间不再查 `SystemParameters.VirtualScreen*`**。`PlaceAroundAnchor`
   改为在 `_dragCacheValid` 时直接用 `OnDragStart` 缓存的那份屏幕边界（每帧省 4 次系统查询）。
4. 因为第 2 点，`Left/Top` 两个 DP 会在拖动中落后于真实位置，所以新增
   `SyncLeftTopAfterRawMove()`，在 `OnDragEnd` 里**补渲染之前**调用一次 ——
   否则松手后 `Reposition → AnimateTo` 会拿旧坐标当动画起点，岛会先跳回起拖点。

顺手加的保险（都不是性能问题，是「改完可能留下坏状态」）：

- `LostMouseCapture` 兜底：拖动中被隐藏 / 捕获被抢走时收不到 MouseLeftButtonUp，
  `_dragging` 会永远停在 true，之后**再也拖不动**。现在会自动收尾。
- `OnDragStart` 开头也同步一次 `Left/Top`，防止上次异常中断留下的旧值。
- `ScheduleCollapse` 的 tick 里挡掉 `_dragging`（见上一节）。

## 2026-11-05（补三）· 拖动优化第一版是错的：更正 + 重新校准

### 一、错在哪

上一节（补二）把「一帧搬十几次窗」当成唯一根因，删掉了 `MouseMove → FollowCursor`，
只留 16ms 定时器。用户反馈：**更掉帧了**。

已立刻回退到 `E:\dsh\backups\20261105-150620-islet-install-before-drag-opt\`。

### 二、新工具 `islet/tools/Cadence` 量出的关键事实

上一版 DragCost 的端到端测法不可信（`CompositionTarget.Rendering` 是按需触发的，
窗口静止时根本不开帧，才会量出「静止 33fps / 移动 57fps」这种自相矛盾的数字）。
新增 `Cadence`，用真实消息循环分四段各 2 秒：

| 阶段 | 内容 | 结果 |
| --- | --- | --- |
| P1 | 只数 Rendering（什么都不动） | 33.0 帧/秒，maxGap 47.9ms |
| P2 | 16ms 定时器 + `SetWindowPos` + 数 Rendering | 51.0 帧/秒，搬窗 **39.5 次/秒** |
| P3 | 16ms 定时器 + `Left/Top` + 数 Rendering | 88.0 帧/秒，搬窗 **39.5 次/秒** |
| P4 | 16ms 定时器 + `SetWindowPos`，不数 Rendering | 搬窗 **39.5 次/秒** |

**决定性的一条是 P4：所谓「16ms 60fps 定时器」在这台机器上只有 39.5 次/秒（≈25.3ms）。**

`DispatcherTimer` 不是帧时钟：它走 WM_TIMER，粒度约 15.6ms，16ms 的请求会被
凑到 1~2 个 tick 上，实测就在 15.6~31ms 之间抖。而我上一版**把跟随完全交给它**，
于是位置更新从「每个 MouseMove 都跟」（几百次/秒）掉到 39.5 次/秒 ——
比 60Hz 屏幕还慢，动作当然变成一跳一跳。

补充数据：显示器 60Hz（RTX 5060 Laptop，2560×1600）；系统定时器分辨率当前是 1ms
（`NtQueryTimerResolution` cur=10000），所以不是系统节拍粗糙，就是 DispatcherTimer 自己的问题。

### 三、更正后的做法（当前代码）

结论：**不是「搬得太勤」，而是「每次太贵 + 没有上限」**。所以两条都要：

1. **保留 `MouseMove → FollowCursor`**（事件驱动的密度天然高于刷新率）。
2. **在 `FollowCursor` 里给「真正搬窗」加时间闸门** `MoveGateMs = 8`：
   两次搬窗至少隔 8ms → 上限 125 次/秒（比 60Hz 屏幕快一倍，每帧都能拿到最新位置），
   同时把「1000Hz 鼠标 → 每秒上千次 × 0.9ms」这种失控情况卡住。
3. 被闸门挡掉的位置**不写进** `_lastCursorX/Y`（否则那一格会被永久吞掉，
   手停下时窗口会停在上一格）。定时器兜底会在闸门打开后补上最后一格。
4. 上一版为「一帧只搬一次」加的 `MoveWindowRaw` / `SyncLeftTopAfterRawMove`
   **整段删掉**：既然节流已经管住了次数，就没必要再引入
   「Left/Top 与真实位置不一致」这个额外风险。
   （那次微基准仍有价值：单次 `SetWindowPos` 0.52ms vs `Left/Top` 0.91ms，
   以后真要再省，这条路是现成的。）
5. 保留的其它改动（与性能无关，纯收益）：
   `LostMouseCapture` 兜底、`ScheduleCollapse` 挡 `_dragging`、
   拖动期间 `PlaceAroundAnchor` 用缓存屏幕边界（省 4 次系统查询/次）。

### 四、加了拖动遥测（关键）

拖动手感没法靠猜，所以在 `OnDragEnd` 时往 `islet.log` 写一行：

```
拖动统计: calls=… moves=… gated=… | 单次搬窗 平均…ms 最大…ms | 更新间隔 平均…ms 最大…ms | 一帧预算16.6ms
```

读法：

- `单次搬窗 平均` 接近 1ms 而 `更新间隔 平均` 30ms 以上 → 是**更新太稀**（延迟问题）
- `单次搬窗 最大` 十几毫秒 → 是**单次搬窗太贵**（掉帧问题）
- `gated` 很大 → 闸门在起作用（鼠标回报率很高）

有了这行数，下一次不用再猜。

### 五、验证

```

build.ps1 -SelfTest  无 ERROR；中转区宽度证据未变（436 → 624，DELTA=188）
部署后启动            无 ERROR/WARN
```

- 二进制：`E:\dsh\backups\20261105-150620-islet-install-before-drag-opt\`（含 MouseMove、无节流）

## 2026-11-05（补四）· 设置窗也换成液态玻璃

### 一、约束

## 2026-11-05（补五）· 打包成可分发的安装程序

### 一、为什么换了打包方式

旧的 `package.ps1` 用 IExpress：产物是「自解压 + 弹一个黑框 cmd」，
用户看到满屏命令刷过，安全软件也常把自解压包判成可疑，且**没有卸载入口**。

新方案：一个正经的 WPF 图形安装程序（`islet/src/Islet.Setup/`），
把 Islet 的四个文件以 `.resources` 形式**嵌进 Setup.exe 内部**，
分发出去就一个 exe，双击出图形界面。

### 二、产物（`build/dist/`）

| 文件 | 大小 | 用途 |
| --- | --- | --- |
| `Islet-Setup-1.0.0.exe` | 377.5 KB | 安装版，双击 → 图形界面 → 安装并启动 |
| `Islet-Portable-1.0.0.zip` | 174.5 KB | 免安装版，解压即用 |
| `README.txt` | — | 给接收方的说明（做了什么/不做什么/运行要求） |
| `SHA256SUMS.txt` | — | 两个二进制的 SHA256 |

安装版做什么（全部 HKCU，**不需要管理员权限**）：
- 装到 `%LOCALAPPDATA%\Programs\Islet`；可浏览改位置
- 桌面 / 开始菜单快捷方式（三个勾选项，可取消）
- 在「设置 → 应用 → 已安装的应用」登记卸载入口（`HKCU\...\Uninstall\Islet`）
- 可选开机自启（默认**不勾**，与用户当前设置一致）
- 升级时先结束正在运行的 Islet，避免 exe 被占用

卸载脚本由安装器按实际路径生成（不随包带 cmd），边界写死：
只删自己的目录/快捷方式/自启项；配置与日志单独询问、默认保留；
先把脚本复制到临时目录再删自身目录（cmd 不能直接删正在运行的脚本所在目录）。

| --- | --- |
| `Program.cs` | 入口；`--selftest` / `--uninstall` 两个隐藏模式 |

`package.ps1` 流程：build Islet → `ResourceWriter` 把 4 个文件打进

生成便携 zip → SHA256 + README。
用法：`package.ps1 [-Version 1.0.0] [-SelfTest] [-SkipBuild]`。

### 四、这一轮踩到的坑（都靠自检抓出来了）

1. **`.ps1` 编码**：Windows PowerShell 5.1 读无 BOM 的 UTF-8 脚本会按 ANSI 解码，
   中文变乱码并破坏引号配对，报「字符串缺少终止符」，且报错行号完全不对。
   **凡是含中文的 .ps1 都必须存成 UTF-8 带 BOM**；每次 edit 后要重新补 BOM。
   用 `[Parser]::ParseFile` 逐行累积可以精确定位第一处坏行。
2. **`$args` 是 PowerShell 自动变量**：当普通变量用会被宿主行为干扰，
   导致 csc 把整串参数连成一个文件名（CS2021）。改名 `$cscArgs`。
3. **资源命名不匹配**：打包脚本把 4 个文件写进**一个** `.resources`，
   解包代码却按「每个文件一个资源」去找 → 运行时报「缺少 Islet.exe」。
   改用 `ResourceReader` 遍历 .resources 内部的键。
4. **`Path.GetFileName` 陷阱**：资源键是 `Islet.Setup.payload.Islet.exe`，
   分隔符是**点**不是反斜杠，`GetFileName` 会原样返回整串，
   解出的文件名多一截前缀 → 找不到 `Islet.exe`。改成手动去掉前缀。
5. **不要解包到临时目录**：受限环境（本机就是）连 `%TEMP%` 下新建目录都拒绝，
   解包必然失败，且会往安装包所在目录留 `.setup-xxx` 垃圾。
   最终改成**载荷常驻内存**（`Dictionary<string, byte[]>`，才 300 KB），
   安装时直接 `WriteAllBytes` 到目标目录 —— 不碰 TEMP、不写两次、不留垃圾。
6. **自检只验 UI 不够**：加了「真跑一遍 `Installer.Install` 到临时目录」+
   「ShellLink COM 真建一个 .lnk」，目标放在自检输出目录（避开 TEMP 限制），
   装完立即删掉并注销卸载登记。
